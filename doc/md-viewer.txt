INTRODUCTION                                                       *md-viewer*

md-viewer.nvim renders unsaved Markdown source in a persistent headless Chrome
or Chromium page, captures the visible viewport as a PNG, and places that
raster image over a read-only Neovim preview split.

The preview is a browser-rendered PNG surface, not native terminal text and
not an embedded webview. Mouse and keyboard interaction over it
(|md-viewer-interaction|) is forwarded to the persistent Chromium DOM, which
performs hit-testing, search, and link resolution before the viewport is
recaptured. Text highlighting works the same way, but only through vim-like
motions (|md-viewer-visual|) -- there is no click-and-drag selection. That
gives browser-like behavior on a raster surface. Source text remains a normal,
separately editable and selectable Neovim buffer throughout.

The renderer opens no external browser window, starts no HTTP server, and
listens on no port.

The browser makes no runtime network requests under any configuration; remote
images are fetched by the renderer process and inlined
(|md-viewer-remote-images|).

=============================================================================
REQUIREMENTS                                          *md-viewer-requirements*

- Neovim 0.12+. The graphical backend writes to the terminal through
  |nvim_ui_send()|, a 0.12 API; there is no graphical path without it.
- Node.js 22.12+
- an existing Chrome, Chromium, or Microsoft Edge installation on the machine
  Neovim runs on -- over SSH, the remote host (|md-viewer-ssh|)
- a terminal that advertises the Kitty graphics protocol, used without a
  multiplexer -- see |md-viewer-terminals|
- locked renderer dependencies installed with npm ci
- macOS or Linux. Windows has code paths but no test coverage, and terminal
  cell measurement has no Windows implementation.

Playwright browser downloads are intentionally disabled. See README.md for
plugin-manager installation and the required renderer build hook.

CONFIGURATION                                               *md-viewer-config*

md-viewer needs no configuration. On a terminal it recognizes, the default
`image.backend = "auto"` already selects the Kitty graphics path.

Requesting it explicitly is still worth doing, because an explicit backend
that cannot run fails with an actionable error where `auto` degrades quietly
to text: >lua

    require("md-viewer").setup({
      image = { backend = "kitty_raw" },
    })
<
Every option and its default is listed under |md-viewer-options|.
`lua/md-viewer/config.lua` carries the reasoning behind each non-obvious one.
Options are grouped:

    split       Preview position and size
    preview     Pinning, winbar, and loading indicator
    render      Markdown, scale, quality, and scroll behavior
    browser     Existing browser executable and launch timeout
    image       Graphical or cell backend and placement behavior
    sync        Source-following and preview navigation
    security    Local document root and raw HTML sanitization
    terminal    Terminal profile detection and capability overrides
    interaction Mouse/keyboard interaction: selection, search, links, caret

                                                          *md-viewer-backends*
BACKENDS ~

`image.backend` selects how the preview is drawn.

    auto        The default. Prefers a verified `vim.ui.img` API, then the raw
                Kitty protocol on any terminal md-viewer recognizes, and falls
                back to `cells` where neither is available.
    kitty_raw   The supported graphical path, on any terminal advertising the
                Kitty graphics protocol.
    nvim_img    Neovim's experimental `vim.ui.img` API, when the installed
                build exposes both `set` and `del`.
    cells       Terminal-native text and extmark fallback, without browser
                images. Interaction is unavailable here -- there is no DOM to
                hit-test against.

Recognition is inferred from the environment, never probed: Neovim owns
terminal input, so md-viewer cannot read a protocol reply. A terminal with no
Kitty-graphics evidence therefore lands on `cells` under `auto`, and an
explicit `nvim_img` or `kitty_raw` selection never falls back silently -- it
fails with an actionable error instead. `:MdViewerHealth` names the backend it
chose and why.

                                                       *md-viewer-calibration*
CELL CALIBRATION ~

md-viewer places the image over a rectangle of terminal cells and lets the
terminal scale it, so the render is sharpest when it is built against the
terminal's real cell size. That needs no configuration: the cell is measured
from the operating system, via the pixel geometry TIOCGWINSZ carries beside
the row and column counts. :MdViewerDebug reports which of three tiers is in
use, with the numbers behind it:

- `measured`: the terminal reported its pixel geometry. This is the normal
  case on iTerm2, Kitty, Ghostty and WezTerm.
- `env`: MD_VIEWER_CELL_WIDTH_PX and MD_VIEWER_CELL_HEIGHT_PX are both set,
  and override the measurement.
- `estimated`: nothing could be measured -- chiefly tmux and screen, which do
  not propagate pixel geometry, and any Neovim without LuaJIT. The preview
  still renders, from `render.estimated_cell_width_px` and
  `render.cell_aspect_ratio`, but is not pixel-exact.

To override the measurement, give the cell size in CSS pixels -- the
measured size divided by `render.device_scale_factor`, so a 2x display
measuring 14x32 device pixels wants 7 and 16: >sh

    export MD_VIEWER_CELL_WIDTH_PX=7
    export MD_VIEWER_CELL_HEIGHT_PX=16
<
Measure the active terminal profile rather than copying those values;
:MdViewerDebug prints both the measurement and its CSS conversion.

                                                               *md-viewer-env*
ENVIRONMENT VARIABLES ~

Three settings are read from the environment as well as from `setup()`. They
exist for the case configuration cannot serve: one Neovim config shared across
several machines, where the right answer depends on the session rather than on
the config file. Each is overridden by its explicit config option.

MD_VIEWER_TERMINAL_PROFILE
        Terminal profile to use, bypassing environment inference. Accepts the
        same values as `terminal.profile`: iterm2, kitty, wezterm, ghostty,
        warp, generic_kitty, unknown. An explicit `terminal.profile` outranks
        it; a value that is not a known profile is ignored, and the rejected
        value is reported in :MdViewerDebug's `identified by` field rather
        than failing silently. Chiefly useful over SSH -- see |md-viewer-ssh|.

MD_VIEWER_CELL_WIDTH_PX, MD_VIEWER_CELL_HEIGHT_PX
        Cell size in CSS pixels, overriding the TIOCGWINSZ measurement. Both
        must be set. See |md-viewer-calibration| above.

                                                 *md-viewer-overlay-alignment*
NOTIFICATIONS OVER THE PREVIEW ~

With the kitty_raw backend the terminal draws the image, and its negative
z-index places it below text glyphs but above cell background colours, so a
notification floating over the preview would lose its background. md-viewer
cuts the notification's rectangle out of the image. That cut is exact in
cells, but some terminals apply their window margin to text and not to
graphics placements, leaving it slightly misaligned. Two options handle it:

    raw_overlay_bleed_cells   Extra columns cut past a notification's
                              trailing edge so the overhang cannot paint
                              across it. Default 1. The cost is a thin blank
                              gap instead of a flush edge.
    raw_cell_offset_px        Pixel offset at which the image starts inside
                              its first cell, as the Kitty protocol's X/Y
                              placement keys. Cancels the misalignment
                              outright where the terminal implements them,
                              letting bleed drop to 0.
                              Default { x = 0, y = 0 }.

:MdViewerDebug reports both as `cell offset / bleed`. See
docs/troubleshooting.md for how to measure the offset, and
docs/terminal-support.md for what has been measured on which terminal.

                                                     *md-viewer-document-root*
DOCUMENT ROOT ~

`security.document_root` bounds which local files a preview may load as images
or open as links. It defaults to the project enclosing the document -- the
nearest ancestor directory holding one of `security.document_root_markers`
(`.git`, `.hg`, `.svn`) -- falling back to the document's own directory where
no marker is found, and to Neovim's working directory for a buffer that has
never been written. Setting it explicitly always wins.

The project default is what makes an ordinary repo-relative link work: a
document in `docs/` linking to `../README.md` resolves rather than being
refused. Containment is unchanged either way -- both the lexical and the
symlink-resolved path are checked, so `../` and symlinks cannot escape.
Setting it to "/" switches containment off deliberately, so the preview opens
whatever Neovim itself would open; see SECURITY.md for that trade-off.

                                                     *md-viewer-remote-images*
REMOTE IMAGES ~

Remote images need no configuration. When an image's URL is https, the
renderer process fetches the bytes, validates them exactly like a local image
(magic bytes, `max_local_image_bytes`), and inlines them as a data URI. The
browser itself never makes a network request under any configuration.

This covers both `![alt](url)` and a bare `<img src="url">` tag. An `<img>` is
parsed into an ordinary Markdown image regardless of `security.raw_html`, and
carries only `src`, `alt`, `title`, and integer `width`/`height`; it gains no
privilege from being written as HTML.

Only https URLs are fetched, and only if the URL -- and every redirect hop,
should the response be one -- resolves to a public network address; loopback,
private, link-local, and other reserved ranges are refused before a
connection is attempted (see |md-viewer-security|). Redirects are otherwise
followed at most three hops. Fetched images are cached in the renderer
process, so live-preview re-renders do not refetch them.

A fetch never holds the document back. An image that has not arrived by the
time the page is laid out renders as its placeholder, the fetch continues, and
a later render replaces it once the bytes land -- so a slow or unreachable
image costs that one picture rather than the whole preview.

$HTTP_PROXY and $HTTPS_PROXY are deliberately not consulted, so on a network
whose only route out is a proxy, remote images do not load at all: they fail
to their placeholder immediately. The request pins the address it validated,
which is what makes the check above meaningful and what a proxy makes
impossible. See docs/troubleshooting.md, "Remote images never load, and the
network needs a proxy".

                                                         *md-viewer-animation*
ANIMATED IMAGES ~

Off by default. Turn it on with: >lua

    require("md-viewer").setup({ render = { animate = true } })
<
A frame of the preview is one browser screenshot, so an animated GIF or WebP
painted into it is frozen on its first frame. That still frame is what shows
with `render.animate` off, and nothing about the document changes: the image
is inlined, painted and placed exactly as it is with animation on, so the
default costs motion and never a picture.

With it on, the renderer additionally decodes the real frames -- in the same
Chromium that renders the preview, at the size the image is drawn -- and the
terminal draws them itself, on their own layer above the base image and below
the selection highlight. Each frame keeps its own display time from the source
file; nothing is resampled to a canonical tick.

How the frames move depends on what the active terminal was qualified for
(`terminal.animation`, default `"auto"`):

- `native`: the Kitty graphics protocol's animation extension. Frames upload
  once with their gaps and the terminal owns playback -- no timer and no
  per-frame traffic in Neovim at all. Not yet the default anywhere: run the
  `scripts/animation` checklist in your terminal, then opt in with
  `terminal.animation = "native"`.
- `frames`: client-driven. A shared timer swaps which frame is placed,
  honouring each frame's own timing under the `render.animate_fps` ceiling
  (default 5); when the ceiling bites, frames are skipped, never stretched,
  so the animation stays the right length. This is the qualified default on
  iTerm2, Kitty and Ghostty.
- `off`: every animation stays its still first frame.

Chromium still paints the image, so frames are drawn over a picture that is
already correct: wherever animation cannot run, the still frame is what stays
on screen -- there is no hole to fall into. Only the `kitty_raw` backend can
place frames, so animation is unavailable on `cells` and `nvim_img`; it also
needs the terminal's pixel cell size to be measurable
(|md-viewer-calibration|) and a terminal profile validated for natural-size
placements (WezTerm is deliberately excluded -- see |md-viewer-terminals|).
Very long or large recordings are thinned to a fixed pixel budget -- duration
preserved, motion choppier -- rather than allowed to grow the terminal's
memory without bound, and a source past the hard caps stays a still image.

Animation is suspended while a click or a visual selection is in progress, while
a floating window occludes the preview, and while the completion popup is up.
:MdViewerDebug reports the strategy, the layer stack, per-animation state
and, when nothing is moving, `animation_suppressed_reason`.

An image that is refused or fails shows a visible placeholder naming the
reason: a dashed border for a policy refusal (a non-public destination,
non-https), a solid border for an attempted fetch that failed (unreachable,
timed out, too large, not a valid image). See docs/troubleshooting.md.

Previewing a document that references a remote image sends that host a
request, which discloses that the document was viewed. Read SECURITY.md for
this and the other trade-offs.

COMMANDS                                                  *md-viewer-commands*

                                                             *:MdViewerToggle*
:MdViewerToggle [position]
        Open or close the active preview. Position can be right, left,
        below, or above. This is the only command that changes whether a
        preview is showing.

        To open or close one from an autocmd or another plugin, call the
        Lua API rather than this command: >lua

            require("md-viewer.controller").open("right")
            require("md-viewer.controller").close()
<
        `open()` is idempotent -- it returns the existing preview rather
        than opening a second one, and never closes one, which is exactly
        where it differs from :MdViewerToggle.

                                                               *:MdViewerCopy*
:MdViewerCopy
        Copy the current preview selection to the unnamed register, and to
        the system clipboard register when one is configured. A clean
        notification, not an error, when nothing is selected.

        Copying is always manual unless `interaction.copy_on_select` is set,
        which is off by default: silently overwriting the clipboard on every
        selection change would be hostile.

                                                               *:MdViewerFind*
:MdViewerFind [query]
        Search the rendered preview for `query`. Prompts for one via
        |vim.ui.input()| when none is given, also bound to `/` with the
        preview focused.

        The prompt always opens empty -- the previous query is never
        prefilled -- and dismissing it without a query clears both the
        active search and any selection. `<Esc>` with the preview focused
        clears the same two, one press at a time.

                                                           *:MdViewerFindNext*
:MdViewerFindNext
        Jump to the next search match. Also `n` with the preview focused.

                                                       *:MdViewerFindPrevious*
:MdViewerFindPrevious
        Jump to the previous search match. Also `N`.

                                                               *:MdViewerBack*
:MdViewerBack
        Return the preview to the previous document in its history, moving
        the source window with it. See |md-viewer-history|.

                                                            *:MdViewerForward*
:MdViewerForward
        Move the preview to the next document in its history, after going
        back.

                                                             *:MdViewerHealth*
:MdViewerHealth
        Open a short health summary: overall status (healthy/degraded/
        broken), the selected rendering backend, the renderer process, and
        any actionable warnings. Takes no arguments. Round-trips to the
        renderer subprocess. See |md-viewer-health|.

                                                              *:MdViewerDebug*
:MdViewerDebug
        Open the full diagnostic in one buffer: the environment and
        capability detail (raw graphics geometry, cell calibration,
        terminal-profile evidence, Chromium discovery and launch, security
        roots) followed by per-preview session, timing and placement state
        and the event log. This is what to attach to a bug report.

        Selection and search state is reported as lengths and counts only
        -- the selected text is never printed here.

                                                        *:MdViewerMeasureLink*
:MdViewerMeasureLink
        Measure how fast this SSH link carries bytes, and cache the answer
        for this machine. Run it once per machine, from an SSH session, with
        no preview open. The screen floods and then clears; it takes up to
        about a minute and you should not type during it.

        It runs `scripts/ssh-link-speed.sh` in a subprocess writing to the
        pty named by $SSH_TTY, which is the only route that works: the
        answer is not observable from inside Neovim at all, and a subprocess
        Neovim starts has no controlling terminal to reach /dev/tty through.

        Refuses outside SSH, with a preview open, or where no terminal
        device can be resolved -- each of which would measure something
        other than the link. The result lands under |stdpath()| "state",
        keyed by a hash, and is read while `render.ssh_link_bytes_per_sec`
        is "auto". Nothing is written to your configuration.

        See |md-viewer-resident| for what the number is used for.

PREVIEW NAVIGATION                                      *md-viewer-navigation*

The preview has a real caret, and it is a position in the *rendered document*
rather than a terminal cell. It only ever sits on an actual character, and it
is drawn as a block the size of the glyph it is on -- big on an h1, small on
body text. It cannot be parked in the page margin or beside a short heading,
because those are not places a reader can be. Neovim's own cursor is hidden
while that block is on screen and follows along underneath, so focus and
mappings keep working.

                                                          *md-viewer-mappings*
The graphical preview maps these Normal-mode keys. Counts work on every motion
(`10j`, `5w`, `3l`) except gg and G, which always mean the ends of the
document -- going to a source line is a separate feature, not this keystroke
wearing a count:

    h, l, Left, Right        One character, within the rendered line
    j, k, Down, Up           One rendered line, holding its column
    0, $                     Start or end of the rendered line
    w, b, e                  Next word, previous word, end of word
    {, }                     Previous or next block
    CTRL-D, CTRL-U           Half a page
    CTRL-F, CTRL-B           A page
    PageDown, PageUp         A page
    CTRL-E, CTRL-Y           Scroll the view, leaving the caret on its
                             document position
    gg, G                    Start or end of the document (counts ignored)
    H, L                     Back/forward through the preview history
                             (|md-viewer-history|)
    v, V                     Start a selection at the caret, extended by
                             any motion above; V is line-wise
    o                        Swap which end of the selection the caret
                             holds
    y                        Copy the current selection (:MdViewerCopy),
                             leaving visual mode
    /                        Prompt and search (:MdViewerFind)
    n, N                     Next/previous search match

The view scrolls whenever a motion would take the caret out of it, so holding
j scrolls as it always did. CTRL-D and friends are line motions with a count,
as in Vim, so the caret leads and the view follows; CTRL-E and CTRL-Y are the
exceptions, moving the view and leaving the caret on its document position,
where it is simply not drawn until scrolled back.

j and k hold their column through a sticky target, the way Vim's `curswant`
does, so a run down the document and back returns to the character it started
on. Columns are matched on each glyph's left edge, not its centre, because
centres do not survive a change of font size. `$` parks the column past every
line's end, so a following j keeps following line ends down.

h and l stay on the rendered line they start on, as Vim's do under the default
'whichwrap'. A paragraph wrapped over several rendered lines is several lines
here -- the same lines j, k, 0 and $ work on. w, b and e cross lines, as in
Vim.

Clicking moves the caret too, snapped to the nearest real character. Every
motion is one round trip to the renderer, because only the renderer knows
where the characters are; that is what buys the snapping and the glyph-sized
caret.

On a terminal that cannot draw the overlay -- WezTerm, and see
docs/terminal-support.md for the current list -- the caret falls back to the
terminal's own cursor: a fixed cell rather than the glyph, but still on the
right character, and Neovim's cursor stays visible there.

Mouse-wheel events scroll the preview only when the pointer is over its split.

                                                            *md-viewer-visual*
KEYBOARD SELECTION ~

`v` does not enter Neovim's visual mode, and cannot: the preview buffer holds
blank cells, so a real visual selection over it would select spaces. Neovim
stays in Normal mode -- which is what keeps every motion mapping and every
mouse gesture working unchanged -- and the winbar shows "-- VISUAL --" since
Neovim's own indicator has nothing to report. `interaction.visual` gates it.
This is the only way to highlight text in the preview -- there is no
click-and-drag selection.

    v      Start a selection anchored at the caret; any motion extends it
    V      The same, line-wise
    o      Swap which end the caret holds
    y      Copy the selection and leave visual mode
    <Esc>  Leave visual mode, keeping the highlight. A second <Esc> clears it

Each motion resolves an anchor point and a caret point to one real browser
selection, so it gets an instant overlay highlight where the terminal
supports one, a sharp settle frame, copy, and exact source-position
reporting. Extending past the bottom of the window scrolls, so `vG` selects
to the end of the document.

=============================================================================
MOUSE INTERACTION                                      *md-viewer-interaction*

The mouse never highlights text -- only |md-viewer-visual| does that. Every
gesture below is resolved against the live Chromium DOM -- see |md-viewer|.
Each is gated by its own `interaction.*` flag, so one can be disabled without
touching the others.

    Plain click             Places the caret, snapped to the nearest real
                            character; clears an active selection; never
                            moves the source cursor, whether or not
                            anything was selected
    CTRL-click / CMD-click  Activates a link under the pointer: opens
                            http(s)/mailto externally, opens an in-root
                            local file, or scrolls to a same-document
                            fragment. Refuses an unsafe scheme or a
                            document-root escape, with a notification. Does
                            nothing over non-link text. (`interaction.links`)
    Scroll wheel            Scrolls the preview when the pointer is over
                            its split (`sync.mouse_scroll`)

A local Markdown link opens in Neovim, in the source window, and the preview
follows it; CTRL-O returns. Files Neovim has no filetype for, and PDFs, still
go to the system handler via |vim.ui.open()|. A link is never handed to that
handler when the target is something the OS would run rather than display
(|md-viewer-security|), and the root it is checked against is described under
|md-viewer-document-root|.

On macOS the terminal may claim CTRL-click or CMD-click before Neovim sees
it: iTerm2 uses CMD-click to open URLs, and some terminals emulate a
right-click on CTRL-click. If neither activates a link, check the terminal's
mouse settings.

The mouse pointer never changes shape over the preview. Only the terminal
could change it (OSC 22), and support proved inconsistent enough that nothing
is sent; the global 'mousemoveevent' is left alone.

=============================================================================
PREVIEW HISTORY                                            *md-viewer-history*

Following a link retargets the preview, and `preview.pinned` deliberately
stops the preview following an ordinary buffer switch -- so without a way
back, the document the reader came from is only recoverable as text, never as
a rendered view.

    H  / :MdViewerBack       Previous document in this preview's history
    L  / :MdViewerForward    Next document, after going back

H and L are preview-local, installed beside the keys the preview already owns
(`y`, `/`, `n`, `N`, `gg`, `G`), and shadow "top/bottom of screen" -- which
addresses nothing in a scratch buffer holding no text. They are gated on
`interaction.links`. Both commands work from either window, and both move the
source window as well.

CTRL-O works on its own too: when the source window returns to a document
this preview has already shown, the preview follows it back. Deliberately
narrow -- only documents in this preview's own history qualify, so
`preview.pinned` still holds for every other buffer switch.

Navigating from the middle abandons the forward branch, as a browser does.
The list is capped at `interaction.history_limit` (default 32) and records a
buffer and a path per entry, so an entry whose buffer has been wiped still
reopens its file.

=============================================================================
TERMINAL SUPPORT                                         *md-viewer-terminals*

md-viewer.nvim recognizes iTerm2, Kitty, WezTerm, Ghostty, and Warp by
Kitty-graphics-protocol compatibility. The instant selection highlight -- the
selection drawn as translucent overlay rectangles rather than re-photographing
the page each frame -- is enabled only on terminals where an operator drove it
by hand and watched it: iTerm2, Ghostty and Kitty, with
docs/terminal-support.md holding the current list. Everywhere else a selection
falls back to full captured frames, which is always correct and merely slower.

It is off on WezTerm for cost rather than correctness, pending an upstream
fix. Do not force it on there; docs/terminal-support.md has the measurement
and the upstream issue.

Warp is Experimental. Image rendering works. The selection highlight is off
because Warp ignores Kitty placement ids and so cannot replace an overlay
rectangle in place; animation is off on the profile's own conservative
default. A stray
Neovim Visual selection over the preview can blank the image there, which
md-viewer works around by keeping Neovim out of its own visual mode over the
surface. See docs/terminal-support.md.

If preview text renders at roughly twice its configured size, the terminal's
reported cell is being converted with the wrong divisor. Check `cell unit` in
|:MdViewerDebug|, and see |md-viewer-calibration| and the "image is stretched
or soft" section of docs/troubleshooting.md.

tmux, screen, and Zellij are not supported: no escape-sequence passthrough is
implemented for any of them. :MdViewerHealth detects a multiplexer and
surfaces it so the failure is diagnosable.

docs/terminal-support.md holds the per-terminal status, the four evidence
labels this project uses, and what qualifying a new terminal requires. Set
`interaction.selection_overlay` to "on" to try your own, after reading that
option's notes in lua/md-viewer/config.lua.

                                                               *md-viewer-ssh*
REMOTE SESSIONS OVER SSH ~

md-viewer works over SSH. Node.js and Chrome/Chromium must be installed on the
remote host, because by default the renderer runs wherever Neovim runs; it
produces a PNG which Neovim then writes to your terminal as Kitty graphics
escape sequences, travelling down the SSH connection.

The part that needs care is terminal identification, because SSH does not
forward TERM_PROGRAM. It does forward LC_* by default, and iTerm2 and WezTerm
both export LC_TERMINAL for exactly that reason, so those two are recognized
automatically -- provided the remote sshd accepts the variable. Nearly every
distribution ships `AcceptEnv LANG LC_*` already; check with `echo
$LC_TERMINAL` on the remote host.

Kitty, Ghostty and Warp export no forwardable identity, so name the profile on
the remote host: >sh

    export MD_VIEWER_TERMINAL_PROFILE=kitty
<
See |md-viewer-env| for that variable, and `terminal.profile` for the config
equivalent. :MdViewerDebug reports `ssh session` and, when the terminal could
not be identified on an SSH session, a caveat naming these fixes.

Every refresh sends a full-page PNG down the connection as base64, so on a
throttled link the wire time per frame outweighs everything else put together.
On an AWS SSM tunnel, which is flat at 0.80 MB/s, one 80 KB moving frame is
about 134 ms of pure transit and a single wheel spin queues over a hundred of
them -- the backlog is the lag, not the render.

That ceiling is SSM's, not SSH's. It is the SSM agent pacing its output at one
kilobyte per millisecond, which AWS has said they will not raise
(aws/amazon-ssm-agent#664); an ordinary SSH session goes nowhere near that code
and measures 16-23 MB/s to a host on the same network. So "remote" is not a
useful predictor of any of this, and the two adjustments below are applied to
every SSH session only because Neovim cannot tell an SSM tunnel from a LAN hop
-- both arrive as an ordinary SSH session. On a fast link they cost a little
sharpness on a frame that is already moving, which is why they are safe to
apply blind. |:MdViewerMeasureLink| measures yours.

md-viewer therefore does two things differently on an SSH session, both
without configuration. It captures the moving frame of a scroll at half size,
restoring full sharpness once scrolling stops; and it waits longer before
spending that sharp capture, because a mouse wheel delivers notches 50-150 ms
apart and a short delay reads an ordinary gap between two flicks as "stopped",
buying a full-size transfer the next notch immediately makes stale. >lua

    opts = {
      render = {
        -- What an SSH session uses when scroll_scale is unset.
        -- 0.5 is 2.6x to 3x fewer bytes per moving frame.
        ssh_scroll_scale = 0.25,
        -- Pin one factor regardless of session, if preferred.
        scroll_scale = nil,
        -- Idle time before the sharp capture. These are two independent
        -- answers, not a base and an adjustment: for one delay everywhere
        -- set both to the same number.
        scroll_settle_ms = 160,
        ssh_scroll_settle_ms = 400,
      },
    }
<
The settle frame is never reduced, so the picture a reader is looking at is
always full `render.device_scale_factor`. :MdViewerDebug reports
`scroll_scale` and `scroll_scale_source`; read them beside `capture_encoder`,
because the numeric scale needs the cdp_fast_png path and a session that fell
back to playwright_png gets full-size frames whatever is configured.

Two settings switch the scale off entirely rather than tuning it, which is
worth knowing before concluding it does nothing. `render.fast_scroll = false`
leaves no separate moving frame for the factor to apply to, so `scroll_scale`
is ignored -- deliberately, because scaling the only frame there is would
leave the preview permanently soft. `browser.fast_png_encode = false` drops
the session to playwright_png, whose own scale is a two-value enum the
numeric factor cannot reach.

Do NOT lower `render.device_scale_factor` for this. It is a calibration
divisor, not a size knob: lowering it doubles the CSS viewport and makes the
frame larger (measured 80 KB -> 224 KB), and it collapses the moving and
settle captures into one, so the cheap scroll frame stops existing. Raising
`render.debounce_ms` does help, by cutting how many refreshes an edit makes.


                                                          *md-viewer-resident*
WHOLE-DOCUMENT RESIDENT MODE (EXPERIMENTAL) ~

Where the terminal supports it, md-viewer can capture the whole document once
as a handful of chunks, keep them in the terminal's image memory, and turn
scrolling into a placement command. After the warm-up, scrolling costs no
captures and no pixels on the wire -- about 140 bytes per pan, whatever the
link.

Off by default. Turn it on with: >

    require("md-viewer").setup({ image = { resident = "auto" } })
<
What it trades is a long warm-up and a document's worth of terminal image
memory for scrolling that sends nothing. Whether that is a good trade depends
entirely on the link, and by more than most people expect: >

    link                        settle frame    worth it?
    AWS SSM tunnel (0.80 MB/s)      ~508ms      yes -- this is what it is for
    plain SSH, host on the LAN      ~19ms       no -- you would only notice
                                                the warm-up
<
Twenty times apart, so "it is remote" predicts nothing. Measure yours before
turning this on -- |:MdViewerMeasureLink| once per machine, and see
`render.ssh_link_bytes_per_sec` below -- and read `render_path` in
|:MdViewerDebug| to confirm which model a preview actually chose. A measured
link also puts an estimate on the warm-up: the winbar reads `warming 3/12 ~14s`
rather than `warming 3/12`.

Selected once per preview, when it opens, and reported by |:MdViewerDebug| as
`render_path`. It is never re-decided mid-scroll: a preview that switched
rendering model while you were reading would be one whose behaviour nobody
could reproduce. A runtime capture failure demotes it to the ordinary
per-scroll path, one way, and says so.

The winbar counts the warm-up: `warming 3/9`. The frame that measured the
document stays on screen while the chunks behind it are captured -- it is a
picture of where you are, taken by the render that built the plan, and there is
no reason to take it down until the chunks can replace it.

Scrolling into a part of the document that has not been captured yet is the
other case, and it shows an empty pane and `waiting for this page` while it
moves that chunk to the front of the queue. It deliberately does not leave the
previous picture up -- that would present pixels of somewhere else as though
they belonged to where you are now, which is precisely the fault this design
exists to make impossible. The two notices mean different things: grey
`warming` is "there is more coming", yellow `waiting for this page` is "this
pane is blank and here is why".

Animated images do not animate under resident mode. Animation frames are placed
against a single base frame, and a resident screen has none -- it is one or two
crops of chunks that move whenever you scroll. Leave `image.resident` off if a
document's animations matter more than its scrolling.

WezTerm is excluded. wezterm#7953 duplicates a cell's attachment list on every
repeat placement over that cell, and panning is nothing but repeat placements
for as long as the preview stays open. WezTerm keeps the per-scroll capture
path, which is correct and merely slower.

Chunk size is `image.resident_chunk_viewports`, and it is not a first-paint
knob. Measured on Ubuntu 22.04 / Chrome 151, the first capture of a browser
process costs 9,874-16,335ms whatever its size and every later one 116-373ms,
so the renderer discharges that once at startup. What chunk size trades is
per-capture overhead against how long a scroll into an uncaptured region
waits: >
    1x     4.0 Mpx    116ms    396 KB    ~507ms of wire
    2x     8.1 Mpx    266ms    826 KB   ~1058ms
    2.9x  11.7 Mpx    373ms   1218 KB   ~1559ms
<
The wire column is at 0.80 MB/s, the SSM ceiling this feature exists for. On a
link twenty times faster it is twenty times smaller and this knob stops
mattering.

`image.resident_memory_mb` is a heuristic, not a guarantee. It is derived from
13 bytes per resident pixel, measured on iTerm2 3.6.11 / macOS 15 against
synthetic gradients; a sustained-RSS run against a real iTerm2 session
disagreed with that figure by 34x and the discrepancy is unresolved. Kitty,
Ghostty and WezTerm are unmeasured. `image.resident_max_chunks` is the bound
that holds whether or not the per-pixel figure is right, and the chunk you are
reading is never retired.

`render.ssh_link_bytes_per_sec` is how fast your link carries bytes. There is
no way to observe this from inside Neovim: `nvim_ui_send` appends to Neovim's
own UI queue and returns, so on a 0.80 MB/s link, 96 payloads totalling 24 MB
were accepted in 0.03 seconds with no write ever waiting. A plugin timing its
own writes measures a queue insertion and concludes the link runs at ~100 MB/s.
Measure it from the shell instead, with Neovim closed: >

    sh scripts/ssh-link-speed.sh
<
Add `--write-cache` and there is nothing to paste anywhere: it files the answer
under |stdpath()| "state", keyed by a hash of this machine and this link, and
the default `"auto"` reads it from there. |:MdViewerMeasureLink| runs the same
script from inside Neovim and does the same thing.

`"auto"` never measures on its own -- it only reads what one of those two wrote,
so a machine where neither has been run stays "unknown" and nothing happens. It
decides which shell run this machine uses, not whether to take one.

A number set here outranks it, and is never capped against anything. That is
worth naming as a trap rather than a feature: one `~/.config/nvim` symlinked to
several machines makes any number in it wrong on all but one of them, and
silently defeats per-machine detection everywhere. Measured 2026-08-25, an AWS
SSM tunnel carries ~1,030,000 B/s and a LAN host ~14,700,000 -- fourteen times
apart, with no constant that serves both. Set a number only for one machine's
own configuration.

Leaving it unset is a legitimate answer and means unknown. Nothing infers one.

                                                    *md-viewer-ssm-throughput*
Why an AWS SSM tunnel is 0.80 MB/s ~

Because so much of the advice above turns on it. The SSM agent reads at most
`StreamDataPayloadSize` (1024) bytes from your shell or forwarded port and then
sleeps a millisecond before sending more, in both of its output paths. One
kilobyte per millisecond is 1.024 MB/s of ceiling, and real sessions land at
0.6-0.8. An AWS maintainer confirms both the cause and that it is not going to
change in aws/amazon-ssm-agent#664 ("0.6 MB/s speeds on 5 GB/s burstable
instance"), where a reporter on a 27.5 MB/s connection measures the same thing
after ruling out instance type from t3.micro to m7i.8xlarge.

It has nothing to do with SSH. A plain SSH session touches none of that code:
measured 2026-08-25, 8 MB through a pty to a host on the same network took
0.47-0.54 seconds, or 16-18 MB/s. See docs/local-render-design.md for the full
working.

=============================================================================
SECURITY                                                  *md-viewer-security*

The renderer blocks all runtime browser networking unconditionally, disables
browser JavaScript, and disables raw Markdown HTML. Remote images are fetched
by the renderer process rather than the browser, and only from public network
destinations -- never loopback, private, or link-local, on the initial URL or
a redirect hop (|md-viewer-remote-images|). Local images and local links are
confined to a canonical document root (|md-viewer-document-root|). Initial
npm ci installation may contact the configured npm registry.

Mouse and keyboard interaction adds no new attack surface: every gesture
resolves against the same already-sanitized document (nothing re-parses
Markdown or re-touches the filesystem on a click or a selection), local-file link
activation re-checks the document root the same way image loading does
(symlinks included), and search and selection text is always handled as plain
text, never interpreted as markup.

A local link is never handed to the operating system when the target is
something it would execute rather than display: macOS bundles and scripts,
Windows executables, .desktop/.AppImage/.jar, disk images, or any file with an
execute bit. Those are refused with a notification.

Read SECURITY.md before enabling `security.raw_html`; :MdViewerDebug reports
it as `overrides: SECURITY RELAXED`.

=============================================================================
HEALTH AND DIAGNOSTICS                                      *md-viewer-health*

Run: >vim

    :checkhealth md-viewer
    :MdViewerHealth
    :MdViewerDebug
<
`:checkhealth md-viewer` and `:MdViewerHealth` both give a short summary -- an
overall status (healthy/degraded/broken), the selected backend, the renderer
process, and any warnings. They answer "is this set up to work here". A
warning means one thing: something may not work, and you can do something
about it.

`:MdViewerDebug` is the full diagnostic and answers "what did it just do": the
environment field by field -- cell calibration, raw-graphics layers, terminal
profile evidence, Chromium discovery, security roots -- plus per-preview
session state, timings, placements and the event log. It is what to attach to
a bug report, and it is where every field name this documentation mentions is
printed.

Neither reports what md-viewer photographed working on which terminal and
date; that describes this project's testing rather than your session, and
lives in docs/terminal-support.md.

Graphical correctness, click accuracy and interaction behavior still require
interactive terminal testing -- a headless check cannot validate rendering,
real mouse input, or flicker. See docs/troubleshooting.md for symptom-by-
symptom guidance.
